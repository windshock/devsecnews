작성 톤/문장 규칙(중요):
- 자연스러운 한국어로 작성한다. 번역투/직역 문장 금지.
- ‘~했습니다/합니다’ 중심의 담백한 공지 톤을 기본으로 한다.
- 문장은 짧게 유지한다. (가능하면 1~2문장 단락)
- 과장 표현/추측 금지. 불확실하면 “확인 불가”라고 명시한다.

[문체/자연스러움 강제 규칙(기계번역 제거)]
- 한국어 고유 어순으로 쓴다. 영어식 명사 수식 나열(“~의 ~의 ~”)을 1문장에 2개 이상 쓰지 않는다.
- “~에 대한”, “~에 대한 답”, “우려에 대한”, “~의 관점에서” 같은 번역투 구조를 피한다. 필요하면 구조를 바꿔 단정형으로 쓴다.
- “~할 수 있습니다/좋겠는데/가능한/우려/제약/종속/안정적으로/무난/편차” 같은 설명체 표현을 최소화한다. 단정형으로 쓴다.
- 메타 진행 문구(“좋습니다/좋은 캐치/목표는/다음으로/원하시면/확인하겠습니다/반영 파일”)는 쓰지 않는다.
- ‘권장합니다/필요합니다/해야 합니다/검토해보세요/고려해보세요/주의하세요’는 쓰지 않는다. 대신 동사로 끊는다: “업데이트합니다. 차단합니다. 기록합니다.”
- 한 문장에 정보가 2개를 넘으면 문장을 분리한다.
- 같은 문단에서 ‘합니다’가 3번 연속 반복되면 다시 쓴다(동사 교체/문장 분리).
- 명사형 종결(“~가능.” “~필요.”)은 쓰지 않는다.
- 각 항목/단락의 마지막 문장은 즉시 조치로 끝낸다(업데이트합니다/차단합니다/설정을 바꿉니다/키를 교체합니다/룰을 추가합니다).

[용어 표준(표현 통일)]
- “안전 설정”은 쓰지 않는다. “보안 설정”으로 쓴다.
- “안전한 대안”은 유지한다(코드 예시 구분 용도).
- XML 관련 조치는 아래 표현으로 쓴다.
  - “XML 파서 보안 설정을 강제합니다.”
  - “DTD/외부 엔티티를 비활성화합니다.”
- 격리 관련 표현은 “격리” 또는 “샌드박스” 중 하나로 고정해 문서 내에서 혼용하지 않는다.
  - 기본값: “격리”로 쓴다(“별도 프로세스/컨테이너로 격리합니다.”).

[자연스러움 자체 검수(출력 전 체크리스트)]
- 출력 직전에 아래 3단계를 수행한다.
  1) 번역투 표현을 단정형으로 재작성한다(“~에 대한” 삭제, “~할 수 있습니다” → “~입니다/~합니다”).
  2) 불필요한 주어를 지운다(“개발자는/사용자는/우리는” 삭제).
  3) 문장을 쪼갠다(문장 길이를 줄이고 1문단 1~2문장으로 만든다).
- 이 체크를 통과하지 못하면 해당 문단을 다시 쓴다.

[추가: 메타/훈계형 결론 금지 규칙]
- “~해야 한다는 신호입니다 / ~의 메시지입니다 / ~라고 볼 수 있습니다 / 시사점 / 교훈 / 경각심” 같은 메타·훈계형 종결을 금지한다.
- 각 항목/단락은 반드시 “즉시 실행 가능한 조치” 문장으로 끝낸다.
  - 허용되는 마무리 예: “업데이트합니다.” “삭제합니다.” “차단합니다.” “allowlist로 고정합니다.” “테스트를 추가합니다.” “권한을 분리합니다.”
- 조치가 2개 이상이면 문장을 나눠 쓴다. 한 문장에 조치를 여러 개 묶지 않는다.
- “권장합니다/필요합니다/해야 합니다”는 최소화하고, 가능하면 “~합니다”로 단정형을 쓴다.
- 독자에게 판단을 넘기는 표현(“검토해보세요/고려해보세요/주의하세요”)을 피하고, 할 일을 적는다.

범위/우선순위:
- CVE는 ‘근거’로 활용하되, 중심은 “취약한 개발 패턴”과 “즉시 적용 가능한 가드레일”이다.
- 단순 뉴스 나열 금지. 각 항목은 (패치/설정/코드/운영 점검)으로 귀결되어야 한다.
- OS/미들웨어/인프라팀 범위의 패치 공지는 제외한다. (중요)
  - 예: OS 커널, JVM 배포/패치, Oracle CPU, WebLogic/Fusion Middleware 같은 “플랫폼 패치 이벤트”는 개발자 문서에 포함하지 않는다.
  - 단, 개발자가 코드/빌드/런타임 설정을 직접 바꿔야 하는 변경(예: 라이브러리 교체, 프레임워크 설정 변경, 코드 가드레일 추가)이 명확할 때만 포함한다.
- DoS/자원고갈(Availability) 유형은 제외한다. (중요)
  - 예: 서비스 중단, 크래시, 리소스 고갈(메모리/CPU/FD)만을 유발하는 이슈는 문서에 포함하지 않는다.
  - 표(CVE/이슈 표), 항목별 설명, 패턴 Top 5, Executive Summary, 공통 트렌드, 체크리스트 모두에서 제외한다.
  - 단, 사용자가 “운영 참고에 DoS도 포함”을 명시적으로 요청한 경우에만 별도 섹션으로 1~2문장만 적는다.

조사 요구사항(출처 규칙 최우선):
1) 반드시 웹에서 최신 근거를 찾아라(공식 릴리스 노트, NVD, vendor advisory, 주요 보안 매체).
2) 모든 항목은 “출처 링크(URL)”가 없으면 작성하지 않는다. (근거 부족으로 제외)
2.1) NVD 링크는 “열렸는지”를 검증한다. (중요)
  - NVD 페이지가 “CVE ID Not Found” 또는 동등한 상태(RESERVED/미반영)로 보이면 NVD 링크로 쓰지 않는다.
  - 이 경우 2차 소스는 아래 중 하나로 대체한다.
    - GitHub Security Advisory(GHSA)
    - 벤더/프로젝트 공지 내 CVE 참조(릴리스 노트/보안 공지)
    - CVE Program의 CVE Record(가능한 경우)
  - “NVD 링크가 안 열린다”는 상황 자체도 사실이므로, 2차 소스는 “확인 가능한 URL”로만 남긴다.
3) 링크 표기 형식을 아래처럼 고정한다. (Markdown에서도 줄바꿈 포함해 동일하게 유지)
   - 각 항목 끝에 반드시 아래 줄을 포함(항목마다 개별 부착):
     [Source] https://... (YYYY-MM-DD)
   - CVE 항목은 가능한 한 2개 링크를 포함:
     [Source] (1차 소스: 벤더/프로젝트 공지) URL (날짜)
     [Source] (NVD 또는 GitHub Security Advisory) URL (날짜)
   - “Sources:”로 뭉뚱그려 나열하지 말고, 항목별로 붙인다.
   - 링크에 날짜가 없으면 (날짜 미표기)로 두고, 가능하면 공지 날짜가 있는 페이지를 우선한다.
4) Node.js와 Java를 분리해 정리하되, 공통 이슈(의존성/SBOM, 업그레이드, CI 보안)는 별도 섹션으로 묶어라.
5) CVE가 있으면 표로 제공하라:
   - 표는 Markdown 표로 작성한다.
   - 열: CVE, 영향 버전, 공격 영향(C/I/A), 악용 여부(in-the-wild), 권장 조치(업데이트/완화책), 관련 CWE, Source URL
   - Source URL 열에는 URL을 그대로 넣는다. (2개면 줄바꿈으로 2줄)
   - DoS 중심 항목은 표 하단에 “운영 참고”로 요약 1줄 처리하거나 별도 표로 분리한다.
6) CVE가 없더라도 개발자에게 중요한 보안 트렌드/사고/악용 캠페인이면 포함하되,
   “왜 개발자가 신경 써야 하는지”를 1~2문장으로 설명하고 반드시 [Source] URL을 1개 이상 붙여라.
   - 단, 설명의 마지막 문장은 반드시 “조치”로 끝낸다.
7) 마지막에 “이번 달 개발자 체크리스트”를 10개 내외로 만들어라(코드/의존성/런타임/배포/관측).
8) 가능한 경우 각 이슈를 CWE로 매핑하고, CodeQL/정적분석으로 탐지 가능한 지점을 한 줄로 제안하라.
   - 예: “CodeQL: 사용자 입력이 eval/Runtime.exec/SQL builder로 흐르는 경로를 탐지”
