# Node.js `async_hooks` 켜진 상태에서만 터지는 “잡히지 않는 스택 오버플로” DoS — 개발자용 설명

> 출처: Node.js 보안/취약점 공지 (2026년 1월)  
> 영향: **재귀(깊이)가 외부 입력으로 커질 수 있는 코드** + **AsyncLocalStorage / APM / OpenTelemetry 등으로 async context 추적이 활성화된 런타임**

---

## TL;DR (개발자 관점 핵심)

- 평소엔 재귀가 너무 깊어지면 `RangeError: Maximum call stack size exceeded`가 **던져지고**, 운이 좋으면 `try/catch`로 잡아 500 처리 후 요청만 죽일 수 있습니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
- 그런데 `async_hooks`(또는 그 위에 있는 `AsyncLocalStorage`)가 활성화된 상태에서 특정 패턴이 겹치면, 이 `RangeError`가 **잡히지 않고** Node가 **exit code 7로 즉시 종료**(프로세스 크래시)할 수 있습니다. `process.on('uncaughtException')`도 건너뜁니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
- Node.js는 2026-01-13 보안 릴리스에서 “스택 오버플로만큼은 fatal로 처리하지 말고 사용자 코드로 다시 throw”하는 완화를 넣었습니다. 따라서 **업데이트가 최우선**입니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))

## 이게 왜 흔한 서비스에서 재현되나?

### 1) 프레임워크가 이미 “요청 컨텍스트 추적”에 AsyncLocalStorage를 쓰는 시대
- React Server Components, Next.js는 요청/렌더링 컨텍스트를 추적하기 위해 `AsyncLocalStorage`를 사용합니다. (ALS는 내부적으로 async context 추적을 합니다.) ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  

### 2) 관측(Observability) 도구가 `async_hooks`를 켠다
- OpenTelemetry는 Node 환경에서 context 전파 메커니즘으로 `async_hooks`나 `AsyncLocalStorage`를 언급/활용합니다. ([opentelemetry.io](https://opentelemetry.io/docs/languages/js/context/?utm_source=chatgpt.com))  
- 실제로 OpenTelemetry에는 `async_hooks` 기반 컨텍스트 매니저 패키지가 있습니다. ([npmjs.com](https://www.npmjs.com/package/%40opentelemetry/context-async-hooks?utm_source=chatgpt.com))  

즉, “재귀로 stack overflow” 자체는 흔한 버그지만, **현대 Node 서버는 기본적으로 async context 추적이 켜져 있을 확률이 높아서** “요청 하나로 프로세스가 죽는” 형태로 변질될 수 있다는 게 포인트입니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))

## 재현 패턴 (아주 단순화)

아래는 Node.js 공지에 있는 재현 아이디어를 거의 그대로 단순화한 것입니다. 핵심은:

- 재귀 호출
- 매 호출마다 `new Promise()` 같은 것으로 “async context 생성(프로미스 훅이 동기적으로 불림)”
- `async_hooks.createHook()`이 enable 되어 있음

```js
import { createHook } from "node:async_hooks";

// APM 도구들이 흔히 하는 패턴을 흉내
createHook({ init() {} }).enable();

function recursive() {
  new Promise(() => {}); // Promise 생성 -> V8 promise hook -> async_hooks 콜백 경유
  return recursive();
}

try {
  recursive();
} catch (e) {
  console.log("원래라면 여기로 와야 하지만…", e);
}
```

- 기대: `try/catch`가 RangeError를 잡음  
- 실제(취약 버전에서): **exit code 7로 즉시 종료**, catch 블록도 실행되지 않음 ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))

## “왜 try/catch도 못 잡고 죽어?” (원인, 개발자 눈높이로)

Node 공지의 설명을 개발자 관점으로 요약하면 이렇습니다.

1. `new Promise()`를 만들면, V8은 내부적으로 “promise hook”을 **동기적으로** 호출합니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
2. `async_hooks`가 enable이면, 그 hook은 Node의 `async_hooks init callback`(자바스크립트 콜백)까지 타고 들어갑니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
3. 재귀가 깊어져 스택이 바닥나면 `RangeError`가 발생하는데, 그 순간 “현재 실행 중인 프레임”이 사용자 함수가 아니라 **hook 콜백 쪽**일 수 있습니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
4. Node는 “훅 콜백에서 에러 나면 매우 위험하니 즉시 종료” 같은 fatal 처리 모드가 적용되는 지점이 있고(공지에서는 `TryCatchScope::kFatal`), 그 경로를 타면 **바로 exit code 7로 종료**합니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  

즉, 에러의 “원인”은 사용자 코드 재귀지만, 에러가 “발생한 순간”의 실행 위치가 훅 콜백이면 런타임이 “이건 복구 불가”로 취급해버리는 케이스가 생긴 겁니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))

## Node.js가 제시한 ‘특이한 관점’ (이 글이 흥미로운 이유)

Node 팀은 이 이슈를 단순히 “Node 버그”라기보다, **생태계가 ‘명세에 없는 동작’을 가용성 보장처럼 기대해 온 문제**로 프레이밍합니다.

- “스택 오버플로가 ‘catchable error’로 복구된다”는 건 JS/V8이 best-effort로 해주던 동작이지, 보안/가용성 보장으로 의존하면 안 된다는 주장입니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
- 그래서 패치는 “항상 잡히게 보장”이 아니라, **‘async_hooks on/off에 따라 다르게 죽는 불일치’를 줄여** 재현 가능성을 낮추는 ‘완화(mitigation)’에 가깝다고 말합니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  

이 관점은 개발자에게 “업데이트”뿐 아니라 **코딩 스타일/방어 로직(재귀 깊이 제한 등)**을 바꾸라고 촉구하는 메시지로 이어집니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))

아래 중 하나라도 해당하면 “조건만 맞으면” 영향권입니다.

> 조직 표준이 없다면, “현재 운영 중인 LTS 라인”에서 해당 보안 릴리스 이상으로 올리는 게 목표입니다.

### 2) 근본: “재귀 깊이 = 입력값” 구조를 제거/제한
Node 공지의 권고는 단순합니다. **재귀를 없애거나(반복으로 변경), 깊이 제한을 두라.** ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  

실무 팁:
- 트리 순회: 재귀 DFS → 명시적 스택 배열로 반복 DFS
- 파싱/정규화: 중첩 구조의 최대 깊이 제한(예: 1000 같은 상한)
- “깊어질수록 promise를 생성하는” 패턴은 특히 위험 신호로 보기 ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  

### 3) 관측 도구가 원인일 때의 현실적인 선택지
- 업데이트 전 임시 완화로 “특정 APM/트레이싱 훅을 끄기”가 도움이 될 수 있지만, 근본 해결은 아닙니다(어차피 프레임워크도 ALS를 쓸 수 있음). ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))  
- Node 24+에서는 `AsyncLocalStorage`가 V8의 AsyncContextFrame 기반으로 재구현되어(ALS 사용 케이스에 한해) 영향을 줄일 수 있다고 설명합니다. 다만 `createHook()`을 직접 쓰는 도구는 여전히 별개입니다. ([nodejs.org](https://nodejs.org/en/blog/vulnerability/january-2026-dos-mitigation-async-hooks))
